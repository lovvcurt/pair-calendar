# Настройка приложения «Вместе» с нуля

В этом руководстве вы создадите аккаунты GitHub и Supabase, подключите базу, проверите приложение на компьютере и опубликуете его как PWA. Пароль базы и ключи нужны только в вашем сервисе или на вашем компьютере. Никому не отправляйте их в чат.

## Что потребуется

Обязательно:

- аккаунт [GitHub](https://github.com/signup);
- аккаунт [Supabase](https://supabase.com/dashboard);
- компьютер Windows, macOS или Linux с Node.js 20 или новее и Git;
- доступ к почте, которую вы укажете в Supabase Auth.

Необязательно:

- собственный SMTP-провайдер для писем подтверждения и восстановления пароля;
- собственный домен. Стандартного адреса GitHub Pages достаточно.

Публичный publishable key можно передавать браузеру. Пароль базы, SMTP-пароль, Supabase secret key и service_role key — секреты. Это приложение никогда не просит помещать секретный ключ Supabase в сайт.

## 1. Создайте аккаунт GitHub и репозиторий

1. Откройте [github.com/signup](https://github.com/signup), создайте аккаунт и подтвердите почту.
2. Войдите на GitHub и нажмите **New repository**.
3. Назовите репозиторий, например **pair-calendar**. Для обычного бесплатного аккаунта проще выбрать **Public**. Если аккаунт или тариф позволяет Pages для private-репозитория, можно выбрать его.
4. Не добавляйте README или шаблон .gitignore при создании: они уже есть в проекте.
5. Установите [Node.js LTS](https://nodejs.org/) и [Git](https://git-scm.com/downloads), если они ещё не установлены.

Загрузить проект можно через Git в PowerShell. Сначала откройте PowerShell и перейдите в папку PairCalendar, которую создаст этот проект. Для текущего пути:

    cd $env:USERPROFILE\Documents\PairCalendar
    git init -b main
    git add .
    git commit -m "Добавить календарь пары"
    git remote add origin https://github.com/ВАШ-ЛОГИН/pair-calendar.git
    git push -u origin main

Замените ВАШ-ЛОГИН и имя репозитория своими значениями. При запросе GitHub может открыть окно входа в браузере. Не записывайте пароль GitHub в команду.

## 2. Создайте проект Supabase

1. Откройте [Supabase Dashboard](https://supabase.com/dashboard), зарегистрируйтесь и подтвердите почту.
2. Создайте организацию, если Dashboard предложит этот шаг.
3. Нажмите **New project**, выберите организацию, задайте имя проекта и надёжный пароль базы данных. Сохраните пароль в менеджере паролей. Выберите ближайший к вам регион и нажмите **Create new project**.
4. Дождитесь состояния готовности проекта. Пароль базы используется только для администрирования/резервного восстановления, он не нужен приложению.
5. Не отключайте Data API: браузерный клиент Supabase обращается к таблицам через этот API. Если Data API был выключен вручную, найдите его в **Integrations → Data API** и включите для нужных объектов.

Официальное руководство Supabase: [создание React-приложения](https://supabase.com/docs/guides/getting-started/quickstarts/reactjs).

## 3. Примените миграцию базы

1. В проекте Supabase откройте **SQL Editor** и нажмите **New query**.
2. На компьютере откройте файл **supabase/migrations/20260928000000_initial.sql**.
3. Скопируйте весь файл, вставьте его в новый запрос SQL Editor и нажмите **Run**.
4. Убедитесь, что запрос завершился без ошибки. Эта миграция создаёт таблицы, ограничения, индексы, функции для приглашений и транзакционного сохранения событий, политики RLS, приватный bucket avatars и список таблиц Realtime.
5. Не создавайте такие же таблицы и политики вручную и не отключайте RLS. Повторный запуск миграции не предназначен для обновления уже настроенной базы: применяйте миграцию один раз к новому проекту.

Проверьте в разделе **Storage → Buckets**, что создан bucket **avatars** с режимом **Private**. Миграция также добавляет правила доступа к нему. Не переключайте bucket в Public и не добавляйте открытое правило чтения.

Realtime-подписка защищена теми же политиками чтения. Миграция включает нужные таблицы в публикацию **supabase_realtime**. Проверьте, что Realtime включён в **Project Settings → Realtime**. Не включайте анонимный доступ к данным ради устранения ошибки подписки.

## 4. Настройте вход по почте

В Supabase откройте раздел **Authentication**.

1. В настройках провайдера **Email** убедитесь, что разрешена регистрация пользователей (**Allow new users**) и включено подтверждение адреса (**Confirm email**). Email-провайдер обычно включён изначально.
2. В **Authentication → URL Configuration** задайте **Site URL**. Для локальной проверки это http://localhost:5173. Перед публикацией измените его на точный адрес GitHub Pages, например https://ВАШ-ЛОГИН.github.io/pair-calendar/.
3. В **Redirect URLs** добавьте оба адреса для подтверждения регистрации и сброса пароля:

       http://localhost:5173/**
       https://ВАШ-ЛОГИН.github.io/pair-calendar/**

   Если у вас пользовательский репозиторий сайта ВАШ-ЛОГИН.github.io, адрес будет https://ВАШ-ЛОГИН.github.io/** без /имя-репозитория/.
4. Сохраните настройки. Не отключайте подтверждение почты для удобства: подтверждённый адрес помогает защитить аккаунт.
5. Для реальной отправки писем настройте собственный SMTP. Стандартный тестовый SMTP Supabase ограничен и подходит не для всех адресов; адреса вне организации проекта могут не получать письма. В Dashboard ищите **Authentication → Emails → SMTP Settings** или настройку **Custom SMTP**. Данные SMTP храните только в Supabase, не в GitHub Pages и не в этом репозитории. См. [официальное руководство SMTP](https://supabase.com/docs/guides/auth/auth-smtp).

При первом входе письмо может попасть в «Спам». Для публичного использования настройте домен отправителя и SMTP у выбранного почтового провайдера.

## 5. Подключите URL и публичный ключ локально

1. В проекте Supabase откройте **Connect** или **Project Settings → API Keys**.
2. Скопируйте **Project URL** и **Publishable key** (ключ вида sb_publishable_...). Допускается старый публичный anon key, если именно он выдан вашему проекту.
3. В папке проекта скопируйте пример файла и откройте его редактором:

       Copy-Item .env.example .env
       notepad .env

4. Впишите URL и ключ в соответствующие строки:

       VITE_SUPABASE_URL=https://ваш-проект.supabase.co
       VITE_SUPABASE_PUBLISHABLE_KEY=sb_publishable_ваше-значение

5. Сохраните файл. Файл .env исключён из Git. Не меняйте ключ на **Secret key** или **service_role** — это ключи сервера, обходящие RLS.

Публичный ключ неизбежно виден в загруженном JavaScript. Защиту обеспечивают политики базы, Auth и Storage, а не скрытие publishable key. Supabase объясняет типы ключей в [документации API Keys](https://supabase.com/docs/guides/getting-started/api-keys).

## 6. Запустите приложение локально

Из PowerShell в каталоге PairCalendar выполните:

    npm install
    npm run dev

Откройте адрес, который напечатает Vite; обычно это http://localhost:5173. Зарегистрируйтесь с подтверждённым email и войдите.

Первый пользователь нажимает **Создать календарь**. Затем он создаёт одноразовую ссылку приглашения и отправляет её партнёру. Второй человек создаёт свой аккаунт на другом устройстве или в другом профиле браузера и открывает ссылку, затем нажимает **Принять приглашение**. Не входите на обоих телефонах под одним аккаунтом: у партнёров отдельные аккаунты.

Ссылка содержит 256-битный случайный код, сервер хранит его хэш, срок жизни — 7 дней, повторное принятие запрещено. Доступ к данным не выдаётся по идентификатору календаря.

## 7. Опубликуйте через GitHub Pages

В GitHub откройте репозиторий, затем **Settings → Secrets and variables → Actions → Variables**. Нажмите **New repository variable** и создайте две переменные:

| Name | Value |
| --- | --- |
| VITE_SUPABASE_URL | Project URL из Supabase |
| VITE_SUPABASE_PUBLISHABLE_KEY | публичный sb_publishable key |

Эти значения публичны по назначению: сборка добавляет их в браузерный код. Используйте только publishable key; не создавайте переменную с Supabase secret/service_role key.

Далее:

1. Откройте **Settings → Pages**.
2. В блоке **Build and deployment** выберите **Source: GitHub Actions**.
3. Убедитесь, что файл **.github/workflows/deploy.yml** находится в репозитории. По умолчанию workflow запускается при отправке изменений в ветку **main**. Если основная ветка называется иначе, измените имя в workflow.
4. Откройте вкладку **Actions** и дождитесь зелёного запуска **Deploy PWA to GitHub Pages**.
5. Адрес появится в выводе workflow и в **Settings → Pages**. Если первый запуск упал, откройте его шаг **Build site**: при ошибке окружения проверьте имена двух Variables и логику Redirect URLs в Supabase.

Workflow выбирает относительный путь сборки для сайта вида username.github.io/repository/ и корневой путь для username.github.io. Поэтому вручную менять базовый URL обычно не требуется. Официально: [настройка источника Pages](https://docs.github.com/en/pages/getting-started-with-github-pages/configuring-a-publishing-source-for-your-github-pages-site) и [пользовательские workflows](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages).

После публикации вернитесь в **Authentication → URL Configuration** Supabase и проверьте production **Site URL** и Redirect URL. Если домен изменён, обновите и Variables при необходимости.

## 8. Установите PWA на телефон

Для установки нужен опубликованный сайт по HTTPS. На localhost PWA также доступна для разработки.

**Android (Chrome):** откройте сайт, нажмите меню ⋮ и выберите **Установить приложение** или **Добавить на главный экран**. В некоторых версиях Chrome появится кнопка **Установить** внутри приложения.

**iPhone (Safari):** откройте сайт в Safari, нажмите **Поделиться**, затем **На экран Домой** и подтвердите **Добавить**. Установка через другие браузеры на iPhone может быть недоступна.

Service worker кэширует оболочку, иконки и загруженные файлы приложения. Он не кэширует ответы Supabase. Без интернета экран может загрузиться, но просмотр актуальных данных и их сохранение требуют подключения; приложение не выдаёт локальную копию за синхронизированную. При обновлении новый service worker заменяет старый кэш.

## 9. Напоминания и системные уведомления

В событии можно задать несколько напоминаний. Для показа системного уведомления откройте **Настройки → Напоминания → Запросить разрешение** и разрешите уведомления в диалоге браузера. Если ранее нажали «Запретить», измените разрешение через настройки сайта в браузере.

Напоминания сохраняются в Supabase и запускают таймер в открытой вкладке. Браузер может приостановить вкладку, а после закрытия приложения таймер не работает. Фоновые push-уведомления здесь не настроены и не обещаются.

Чтобы добавить push позже, потребуется отдельная серверная часть: подписки браузеров (endpoint, p256dh и auth) в таблице с RLS только для владельца; обработчик push-событий в service worker; VAPID-ключи; серверная Edge Function или другой защищённый HTTPS-сервис, который находит сроки и отправляет Web Push; планировщик для этой функции. Публичный VAPID key разрешается передать браузеру, приватный VAPID key хранится только в Supabase Edge Function Secrets. Также потребуется проверка поддержки на целевых версиях Android/iOS, тест HTTPS, сроки действия подписок и удаление отозванных подписок. Пока это отдельная задача настройки и разработки.

## 10. Импорт и экспорт .ics

**Импорт:** откройте **Настройки → Импорт .ics**, выберите файл, проверьте предварительный список и нажмите **Импортировать**. Импортированные события видны обоим участникам. Поддерживаются DTSTART/DTEND, названия, описания, место, UTC, локальные времена и TZID; повторение читает FREQ, INTERVAL и UNTIL. Если правило сложное (например BYDAY, COUNT, EXDATE или RDATE), в предварительном просмотре появится предупреждение, и будет добавлено только первое вхождение.

**Экспорт:** в календаре нажмите **.ics** или откройте **Настройки → Экспорт .ics**. Выберите период и классы событий, затем скачайте файл и откройте его в приложении календаря телефона. Повторяющиеся события за выбранный период экспортируются отдельными вхождениями. Сюрприз/временной блок выгружается только в том виде, который доступен текущему пользователю. Личные записи партнёра не могут попасть в экспорт.

Это перенос копии файлов, а не подключение двусторонней синхронизации системного календаря. Для сложных повторов импортируйте отдельные даты или проверьте предупреждения перед подтверждением.

## Приватность и резервные копии

Каждый запрос к базе проходит Auth и RLS. Календарь нельзя прочитать только по его UUID.

- Таблица **events** содержит автора, время, часовой пояс, повторение и уровень видимости. При **Личное** даже строка события доступна только автору. При **Только занятое время** партнёру отдаются только эти временные поля; название, описание, адрес, место, координаты, категория, теги, цвет и напоминания лежат в **event_details**, которую партнёр не может прочитать по RLS.
- Подробности полностью видимого события читаются партнёром только после наступления **surprise_until**. До этой даты в строке времени нет названия и других подробностей. Та же политика действует на обычные запросы и Realtime-подписки.
- Только автор события может изменить или удалить его. Изменение сохраняет базовую строку и детали в одной транзакции; устаревшая версия вызывает конфликт, а не молча перезаписывает правку.
- Случайный код приглашения хранится на сервере как хэш. В Storage bucket **avatars** закрытый доступ; владелец загружает свой файл, партнёр получает только временную подписанную ссылку.
- Publishable key является публичным. Secret/service_role key обладает повышенными правами и не должен попасть во frontend, .env, GitHub, Pages или чат.

**Резервное копирование:** .ics содержит лишь доступные события и не является полной резервной копией. Он не переносит аккаунты, профили, опросы, голоса, идеи, теги, настройки или аватары. Проверьте в вашем плане Supabase **Database → Backups** и сроки хранения. Для полного восстановления понадобятся база с Auth-пользователями и идентификаторами, Storage-файлы и параметры проекта; скачайте резервную копию и аватары в защищённое место. Храните пароль базы отдельно. Для аварийного переноса создайте новый Supabase-проект, примените миграцию, восстановите базу и файлы Storage и обновите URL/ключ в сборке. Восстановление Auth требует сохранить связи user ID; простой экспорт .ics для этого недостаточен.

## Частые проблемы

| Сообщение или проблема | Что проверить |
| --- | --- |
| «Подключите Supabase» | Файл .env существует в корне PairCalendar, переменные написаны точно, после правки dev-сервер был перезапущен. |
| Invalid API key / Failed to fetch | Скопируйте Project URL и именно Publishable key из того же проекта. Проверьте адрес проекта, доступ в интернет и что проект не приостановлен. |
| Email address not authorized или письмо не пришло | Для тестового SMTP адрес может быть ограничен; настройте Custom SMTP, проверьте папку «Спам» и Redirect URLs. |
| После ссылки email пустой экран входа | Добавьте точный адрес в **Authentication → URL Configuration → Redirect URLs** и повторите письмо. |
| «Нет доступа» или ошибка RLS | Примените всю миграцию под владельцем проекта. Не отключайте RLS; сначала проверьте, что обе учётные записи действительно участники одного календаря. |
| Партнёр не видит новые данные | Проверьте интернет, состояние «Синхронизировано», включённый Realtime и публикацию supabase_realtime. Перезапуск вкладки повторно загружает данные, но не исправляет ошибку политики. |
| Аватар не загружается | В Storage bucket avatars должен быть Private; примените политики из миграции. Размер до 5 МБ и тип JPG, PNG или WebP. |
| GitHub Pages возвращает 404 | Проверьте **Settings → Pages → Source: GitHub Actions**, зелёный workflow и ветку main. Для проектного сайта открывайте URL, содержащий имя репозитория. |
| Событие сохранено, но партнёр не видит название | Проверьте уровень видимости. При busy подробности специально скрыты; у сюрприза дождитесь даты раскрытия. |
| Старые события отсутствуют после импорта | Проверьте даты начала/окончания и часовой пояс. Импорт сначала показывает выборку; приложение не синхронизирует обратно системный календарь. |

## Известные ограничения

- Для входа и синхронизации нужен интернет и настроенный Supabase. Автономное редактирование и последующее слияние офлайн-правок не реализованы.
- Системные напоминания работают при открытом приложении и выданном разрешении; фоновые push требуют перечисленной выше инфраструктуры.
- Email signup и сброс пароля требуют доставляемой почты, для публичного запуска настройте SMTP.
- Встроенный календарь показывает повторы по FREQ/INTERVAL/UNTIL. Импорт сложных RFC 5545 правил вроде BYDAY/COUNT не полностью поддерживается.
- Партнёр может читать общие события, но редактировать/удалять событие может только его автор.
- GitHub Pages размещает статические файлы и не может запускать серверную функцию, приватный ключ или push-планировщик.
